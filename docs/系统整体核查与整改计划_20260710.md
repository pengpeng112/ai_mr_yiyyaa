# 系统整体核查与整改计划（2026-07-10）

## 1. 核查范围与结论

本次对 FastAPI 应用、RBAC、Dify 推送、调度/通知、数据留存、容器部署、依赖和自动化测试进行了静态代码审查及本地回归核验。

结论：当前版本的业务主链路具备基本可用性，但不满足生产医疗数据系统的安全上线条件。必须先完成 P0 项，再允许新环境部署或扩大访问范围。

本次未访问生产数据库、Dify、业务 Oracle/PostgreSQL，也未执行渗透测试或容量压测；以下问题以代码和部署定义为证据，生产配置与运行状态需在整改验收时补充核验。

### 5.1 密钥迁移与回滚

1. 仅在受控维护窗口执行；先离线备份 `config.json`、备份文件和当前 `SECRET_KEY`，并验证备份可由旧密钥解密。
2. 使用一次性迁移工具，在内存中以旧密钥解密 `password_enc`、`api_key_enc`、`secret_key_enc`，再以新密钥重新加密；迁移前后对非敏感字段做一致性校验。
3. 先在预发布环境使用新密钥启动并完成 Oracle、Dify、通知、前置机连通性测试，再切换生产。
4. 旧密钥仅在受控、限时的回滚窗口保存；窗口结束后按密钥管理要求销毁，并记录轮换审计。
5. 迁移失败不得覆盖原配置；使用镜像、配置和旧密钥进行整体回滚。

### 5.2 通知 SSRF 的兼容原则

1. 普通用户不得提交任意 URL、请求头或认证信息。
2. 通知测试接口仅允许 `manage_config` 权限，并只能测试已保存、已审核的渠道配置。
3. 目标使用显式白名单而非“禁止所有私网地址”：医院前置机和经批准的内网 webhook 可按精确主机/IP、端口、协议登记。
4. 解析 DNS 后仍须校验实际连接地址；禁止回环、链路本地、元数据地址、重定向到非白名单目标和自定义敏感头。

### 5.3 推送与通知状态机最低要求

1. 推送使用业务确认后的幂等键，先原子 claim，再调用 Dify；claim 具有 `pending`、`processing`、`success`、`failed`、`cancelled` 状态和超时恢复策略。
2. 外部通知和前置机投递必须采用 outbox；业务数据先提交，再由独立投递器进行原子 claim 和发送。
3. outbox 至少定义 `pending`、`sending`、`success`、`retry_wait`、`dead_letter` 状态，记录幂等键、尝试次数、下次重试时间、最后错误和人工重发记录。
4. 不得以“消息恰好一次”为目标；目标是业务侧可证明的幂等投递和可恢复的至少一次处理。

### 5.4 生产核验清单

1. 实际 `ENVIRONMENT`、JWT/SECRET_KEY 强度、CORS 来源、`ENABLE_SCHEDULER`、Dify 完整日志开关均与变更单一致。
2. 仅网关可访问应用端口；TLS 证书、反向代理头、Swagger 策略和来源白名单验证通过。
3. 容器为非 root 应用用户运行；`.env`、配置、数据、日志目录权限满足最小权限要求。
4. 无默认管理员、默认密钥、明文通知凭据或包含病历正文的默认日志。
5. 备份可恢复；密钥迁移、数据库迁移、镜像回滚和配置回滚均在预发布演练通过。
6. Dify、业务数据源、前置机、通知渠道的连通性测试只使用批准的测试患者或脱敏样本。

## 6. 上线门禁

以下条件必须全部满足，才允许恢复自动调度和对医院业务网开放服务：

1. P0 全部关闭，并有自动化回归测试。
2. TLS 网关、网络访问控制和主机目录权限经运维复核。
3. 生产环境不存在默认账号、默认密钥或明文通知凭据。
4. 跨科室越权、SSRF、JWT 伪造和敏感日志检查均通过。
5. 推送幂等、调度锁、告警投递、留存清理在预发布演练通过。
6. 完整备份、恢复和回滚演练通过，且由业务、信息安全、运维共同签字确认。

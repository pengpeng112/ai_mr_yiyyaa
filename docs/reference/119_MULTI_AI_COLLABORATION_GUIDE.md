# 119 — 多工具、多模型开发与文档维护指南

> 现役协作指南；更新：2026-10-02。授权及红线以 [AGENTS.md](../../AGENTS.md) 为准，登记制度以 [00_AI协作规则.md](../../开发起步包/00_AI协作规则.md) 为准。本指南不授予生产写入、临床裁决、外发或 Git 写操作权限。

## 1. 工具和模型分开记录，共用仓库事实

ZCode（用户也称 zcod）、Codex、Claude 及其他开发客户端是操作工具；GPT、Kimi、GLM、Grok、Claude 等是模型或产品系列。接手记录写实际组合，例如 `ZCode / GLM（版本未知）`，不能从客户端名称推断模型。模型名未知就写未知，不自行补版本。

所有组合共用下面的文件，不为每个模型复制一套项目规则。不同客户端的聊天记忆、私有 memory 和缓存不会因此自动互通；跨工具交接依赖仓库中的记录。在另一个克隆或机器上工作时，也必须先确认已获得对应文件版本；未提交的本地记录不会自动同步。

| 信息 | 唯一维护位置 | 何时更新 |
| --- | --- | --- |
| 授权、技术约束、规则优先级 | `AGENTS.md` | 经用户授权调整规则时 |
| 启动顺序、任务路由、目录地图 | `开发起步包/README.md` | 入口或分类变更时 |
| 协作、登记、隐私与 Git 规则 | `开发起步包/00_AI协作规则.md` | 经用户授权调整规则时 |
| 已发生的改动事实 | `开发起步包/01_统一修改记录.md` | 每个修改批次或离开会话前追加，不改历史行 |
| 当前会话的负责者、文件范围、恢复点 | `开发起步包/02_协作任务板.md` | 开工、交接、中断、完成时 |
| 文档编号、业务任务状态、归档位置 | `docs/INDEX.md` | 新文档、状态变化和移动时 |
| 当前契约与回归基线 | `docs/reference/`、`docs/skills/` | 有代码、配置或验证证据支持时 |
| 原始验证、前镜像、长任务检查点 | `review/<任务ID>/` | 每批验证后；不入 Git |

任务板管会话协作，INDEX 管业务文档状态，01 管修改历史。三者各司其职：任务板不能变成第二份全系统待办，任务板的 DONE 也不等于生产部署或临床验收完成。

## 2. 各工具接入方式

| 使用方式 | 入口与接手方法 |
| --- | --- |
| Codex 或可读取仓库规则的代理 | 从根目录 `AGENTS.md` 开始，按其启动顺序读取；额外读取任务板 |
| Claude 开发客户端 | `CLAUDE.md` 首部指向共同启动流程；其模块地图仅作参考 |
| ZCode / zcod 或其他本地客户端 | 打开同一仓库，将下方提示词作为项目指令或会话第一条指令 |
| GPT / Kimi / GLM / Grok 等切换模型 | 继续使用同一任务 ID，更新执行者，核对工作区差异与检查点后再动文件 |
| 不能读取仓库的网页或外部模型 | 仅提供经人工核查的脱敏任务说明和必要片段；回复视为建议，由有仓库权限的执行者复核落地并登记 |

不依赖未经验证的客户端自动读取行为，也不新增猜测的 `GROK.md`、`KIMI.md`、`GLM.md` 等入口。工具专属规则只有在实际需要且格式已确认时才设置短指针；共同规则继续维护一份。`.agents/skills/` 是仓库技能资产，各客户端是否自动发现需分别确认；不能调用技能的客户端可直接读取对应 `SKILL.md` 执行规程。

复制给任何开发 AI 的启动指令：

```text
你正在 Med-Audit 仓库工作。先读 AGENTS.md → 开发起步包/README.md →
开发起步包/00_AI协作规则.md → 01_统一修改记录.md 末10行 → docs/INDEX.md，
再读 开发起步包/02_协作任务板.md 及本任务的计划/交付/检查点。
先做 git status --short、git diff --stat，确认已有改动归属。
在任务板登记任务ID、实际工具/模型、文件范围、检查点及用户授权边界。
共用仓库事实，不把历史计划、旧批准、聊天记忆当成本次授权。
范围不重叠的可逆工作自主完成；遇到同文件占用或归属不明，保留现场，
报告具体冲突，并继续不依赖冲突的工作。不要覆盖其他人的改动。
每批保存检查点；修改后验证、同步INDEX、追加01登记、更新任务板。
结束时说明已完成、验证、未完成、恢复第一步和是否提交。
生产写入、临床裁决、外发及commit/tag/push/PR遵守AGENTS的明确授权要求。
```

## 3. 接手、同时开发与中断恢复

1. 开工：检查任务板是否已有相同文件范围的 `RUNNING` 或 `HANDOFF` 项；核对登记、HEAD、工作区差异和前镜像。由同一执行者保存本批 before/哈希，避免用 Git HEAD 覆盖其他人的未提交成果。
2. 认领：新增唯一任务 ID（建议 `日期-主题-序号`），分别记工具、模型、实际负责范围、授权来源、证据和下一步。已存在任务由接手者更新，不另造重复待办。
3. 执行：长任务每个可复核批次更新检查点，并在01追加已经发生的文件修改。验证失败记真实退出码；`NOT_RUN`、`SKIPPED` 不能写成 PASS。
4. 交接：先落盘改动事实，再把任务板标为 `HANDOFF`，列清已完成、未完成、失败命令及恢复第一步。接手者只读复核后改为 `RUNNING`。旧负责人离线或时间过久都不意味着可以自动抢占文件。
5. 完成：验证与登记完成后改为 `DONE`，注明是否提交。业务遗留项放原计划/最新报告，由 INDEX 导航，任务板仅保留链接。

状态：`TODO / RUNNING / HANDOFF / BLOCKED / DONE / CANCELLED`。BLOCKED 只描述受阻范围，写缺少什么和恢复动作；不擅自改变其他分支状态。

任务板是人工协作约定，不是原子锁。两个客户端同时写同一工作区时，应由一个协调者认领与写入任务板、INDEX、01等共享文件；其他执行者提供待登记信息。业务文件范围尽量互不重叠；确需同文件修改时先约定分工或独立工作区。建立涉及 Git 写操作的隔离环境仍遵守 AGENTS 的授权要求，不能把“隔离开发”当作自动 commit/merge/push 批准。

交接模板（放到已有计划、报告或 `review/<任务ID>/exec-log.md`，不要每轮新增一份重复总结）：

```text
任务ID / 工具 / 模型 / 日期时间与时区：
用户目标、范围、验收与授权来源（哪些动作已批准）：
环境 / HEAD / 开始时已有改动及归属：
本批修改文件 / 前镜像与哈希：
已完成（区分本地实现、部署、业务验收）：
验证命令 / 退出码 / 时间 / 证据路径 / 跳过项：
未完成 / 阻塞原因 / 所需输入：
恢复第一步（明确文件或命令）：
生产写入及回滚点 / Git提交情况：
INDEX与01登记位置：
```

## 4. 各类文件怎么放

| 类别 | 位置 | 维护方式 |
| --- | --- | --- |
| 仓库级入口、架构、部署、代码风格 | 根目录已有 Markdown | 保留约定文件名；不将部署入口搬进 archive |
| 共同启动与协作 | `开发起步包/` | 只留稳定入口、记录和任务板；已结束 PROMPT 入 archive |
| 正在执行、受阻计划、仍被引用的交付证据 | `docs/ACTIVE/` | 以 INDEX 状态判断用途；不把 ACTIVE 等同 TODO |
| 长期有效契约、规则与基线 | `docs/reference/`、`docs/skills/` | 更新到现役资料，避免把交付报告当永远有效的实现说明 |
| 已完成或被替代计划、历史提示词 | `docs/archive/<主题-日期>/` | 原文迁移，保留编号、来源、承接文档和哈希 |
| 主服务、前端、独立预检、设计 | `app/`、`frontend/`、`prearchive_service/`、`design/` | 按运行边界分类，保留各模块原目录与测试 |
| 静态发布资源、SQL、工作流与提示词 | `static/`、`docs/sql/`、`docs/*.yml`、`prompts/` | 属于产品资产；不按“看起来旧”直接删除 |
| 运维脚本、测试、固定样例 | `scripts/`、`tests/` | 新运维脚本带日期；测试样例必须脱敏 |
| 配置实例、备份、数据库、日志 | `config/`、`data/`、`logs/` | 保留运行位置、加密值和历史备份；区分模板与实例 |
| 证据与附件 | `review/`、`docs/remediation/`、`docs/attachments/` | 按00规则落位；遵守隐私和提交限制 |
| 工具私有设置、依赖、驱动和离线包 | 启动 README §3 对应目录 | 不作为共同事实源，不凭隐藏目录名或体积删除 |

根目录 `user.xlsx` / `user_dict.xlsx` 及归属未明工具资产继续保留原位，不读取患者内容、不代替所有者决定迁移。

归档条件：有明确完成/替代证据；仍适用的结论已有现役资料承接；没有未解决的内容归属；核对入站引用与路径。可同时满足“本地计划完成”和“报告仍有外部事项”，此时归档计划、保留报告为恢复入口，不把外部事项改成 DONE。仍承担现役规则/契约的旧计划先保留，直到完成承接。

步骤：保存原文与 SHA-256 → 逐文件迁移到主题目录 → 记录 old/new/承接文档 → 更新 INDEX 和现役导航 → 校验哈希、路径及登记。历史报告/01中的旧路径按当时事实保留，通过 INDEX 的归档映射解析；不批量重写历史记录。

## 5. 维护与验证

从仓库根目录执行：

```powershell
python scripts/check_documentation_20261002.py
python scripts/run_gates_20260906.py --quick
git diff --check
```

文档检查器只读检查 INDEX 表格路径、现役文档登记、导航中的本地 Markdown 链接及本次归档映射/哈希；不读取附件、配置秘密、数据库或患者资料，不执行网络访问。历史正文的文字路径、章节锚点、业务状态真实性及并发锁不在自动校验范围内，仍须人工核查。检查器没有自动整理或修复模式。

每次文档变更执行检查器和 gates 技能规定的验证；代码/脚本变更另做相关定向测试。这里的检查器是文档专项校验，正式门禁汇总仍由 `run_gates_20260906.py` 产生。本次未改聚合门禁或 CI，避免扩展既有验收标准。

## 2. 五条对接路径评估

### R1 数据库轮询 + 企微推送（026 方案 B 落地版）——**推荐首选，2 周内可上线**

- 机制：Med-Audit 高频轮询 jhemr 库新提交/签名文书 → 跑 026 的 A 类确定性规则（缺文书/时限/空项/重复，纯代码秒级）→ 经现有 Relay/企业微信通道推给书写医生；B 类语义检查仍走每日批。
- 已具备：**读库链路已在生产运行**（177:5432，每天六类质控在用）；Relay 推送链路成熟；A 类规则即 026 P1。
- 待确认：①文书"提交/签名"状态字段与时间列（v_blws 或文书表状态列，需一次只读核验）；②177 副本同步延迟（分钟级可接受则直接用；否则需开通 179:1521 只读）；③"提交"在 JHEMR 语义里的锚点（保存≠提交≠签名，与质控科确认提醒时点）。
- 风险：低（全部在 Med-Audit 侧）；提醒是"推送给医生"而非"弹窗拦截"。

### R2 复用 CDSS 通道（jssdk）——**UX 最优，需院内协调**

- 客户端已从院内静态服务器 10.10.10.97 加载 `jssdk_cdss_4.0.js`。若该服务器归信息科管理，可在同机制下挂载质控提醒 JS 模块（或在 8.84 提供轻量 check API 供其调用），提醒形态与医生已熟悉的 CDSS 提示一致。
- 依赖：信息科配合改 jssdk 或与惠每协调；网络需放通客户端→Med-Audit 的 API 调用（当前 HTTP 层有拦截策略，需走网络申请，嘉和 docs/14 已有申请清单先例）。
- 定位：R1 跑通后的体验升级（弹窗/嵌入式提示替代企微消息）。

### R3 客户端 IL 补丁——技术可行，运维与责任风险高，仅限单机试点

- 技术上无障碍：无强名称签名，dnSpy 可直接在"保存/提交"流程注入调用 Med-Audit check API + CefSharp/WinForms 弹窗（docs/08 已给出三个同类补丁方案先例）。
- 硬伤：①全院客户端如何分发补丁、嘉和版本升级即被覆盖（每次升级重打）；②医疗软件修改的合规与维护责任；③360 等安全软件拦截（工作区已实测拦截自编译 exe）。
- 结论：不建议作为生产路径；如做，仅质控科单机试点验证交互原型。

### R4 服务端接口（179:86 JHWebInterface 模式）——服务端回调通道

- 院内自建集成先例（XML 配置 + 视图 + 出站 POST），理论上可加"文书提交事件 → POST Med-Audit"项目；但该站是回传型调度（按出院时间窗扫），**无客户端弹窗能力**，且当前 HTTP 层被拦。
- 定位：作为 R2/R5 的服务端配套（EMR→Med-Audit 的可靠投递），不解决"事中提醒"本身。

### R5 嘉和厂商正式定制（178 jhservice 提交事件回调）——最正规、周期最长

- 走嘉和商务/定制流程，在中间件层加提交事件回调。授权/环境事实已摸清（docs/31：178 可达，EMRV6 授权至 2124），但定制开发周期与费用不可控。
- 定位：终态方案，与 R2 二选一。

## 4. 风险与红线

1. 所有路径在获批前**只做只读分析**；客户端程序目录（嘉和工作区）只读，运行实验一律用副本（该工作区既有约定）。
2. 提醒内容遵循 026 严重度映射：默认 low/medium，高危仅限安全类且过 High Gate——**不在提交环节制造红色噪音**。
3. R1 轮询频率与 SQL 需走 jhemr 只读账号限量查询（复用 Med-Audit 现有数据源配置），避免给副本库加压。
4. 涉及网络策略变更（放通 8.84 API）须走正式申请（参考嘉和 docs/14 清单模式）。

## 5. 结论

"医生提交病历时提醒"**不需要等嘉和厂商**：R1（库轮询+企微推送）用现有已验证链路 2 周内可上线，覆盖 026 的 A 类规则（占人工高频扣分约一半）；R2（CDSS jssdk 通道）是体验最好的正式形态，依赖院内协调而非厂商；客户端补丁技术可行但运维风险高，不建议生产使用。嘉和逆向工作区已把客户端/接口/中间件/网络现状全部摸清，本分析的每个判断都有落盘证据可查。

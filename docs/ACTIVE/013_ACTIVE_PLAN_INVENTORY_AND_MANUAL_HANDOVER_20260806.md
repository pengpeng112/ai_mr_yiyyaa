## 2. 当前唯一建议执行主线

### 阶段 A：完成 011/P5 正常运行观察

目标：证明 19c 和可靠性补丁在正常 `daily_increment`、`discharge_final` 中稳定，而不是仅通过连接探针。

1. 连续观察至少 3 次同类型正常调度。

3. 出现 `ORA-12609`、类型失败却总览成功、部分结果或重复当前结果时停止。
4. 此阶段禁止历史补推和全量手工推送。

### 阶段 B：完成 012/P0–P1 基线和 DBA 只读实测

目标：证明新护理和病程查询在真实执行计划、重复耗时和返回数量上满足门禁。

1. Oracle 护理查询：`docs/sql/15_nursing_record_v1_readonly_select.sql`（窄字段基线）和 `docs/sql/17_nursing_record_v2_readonly_select.sql`（兼容性候选）。

3. 先冻结生产六类配置、镜像和 SQL/config hash，关闭字段编码和原关联键一致性缺口。
4. 记录中位耗时、较慢 5% 和最慢 1% 的耗时；确认先筛 patient/visit/时间再进入大表。
5. 本轮查询体已通过静态只读校验，但尚未在生产执行，不能把“静态 PASS”写成性能 PASS。
6. 012/P0 和 P1 未通过前，禁止进入 012/P2 代码切换或 012/P4 影子。

### 阶段 C：012/P2–P3 本地实现与回归

目标：实现标准 Adapter、RelationPolicy、feature flag、源级诊断和回归测试，默认仍使用旧生产来源。

2. 病程范围固定为三个 `mr_class`，事件时间为 `caption_date_time`。
3. 护理保留 `form_time`、`created_date`、模板 572/709 和现有 12 个节点映射。
4. 不调用真实 Dify、不写 PushLog、不发企业微信/H5。

### 阶段 D：012/P4 院内影子对账

目标：旧来源与新来源同日期、同科室只读运行，按记录和关系边解释差异。

1. 只输出聚合、不可逆哈希和差异原因，不输出患者键或正文。
2. 按用户决定，不准备人工脱敏样本。
3. 至少覆盖 7 个业务日、在院/出院、572/709 和三个 `mr_class`。

### 阶段 E：012/P5–P6 小批和分类型上线

1. 首批 20–50 个 bundle，`alert_policy=suppress`。
2. 先切病程来源，护理保持旧来源；通过后再切护理。
3. 每个类型独立配置版本、影子报告、canary 记录和回滚点。
4. 未取得系统负责人批准，不得切换生产。

### 阶段 F：007/008 历史恢复

只有 A–E 对应门禁通过，且另行批准历史范围后才能进入：

1. 先生成 preview、manifest 和 candidate hash。
2. 仅补能按原 patient/visit/时间关系可靠关联的历史数据。
3. 无法可靠关联的历史范围记录数量和原因后跳过，禁止猜键。
4. 先单日/单类型小批，再逐日扩展；不得一次性运行数月全量。

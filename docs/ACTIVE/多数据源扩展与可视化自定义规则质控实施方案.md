# 多数据源扩展与可视化自定义规则质控实施方案

> 版本：v1.1（复核修订版）

## 0. 背景与目标

当前系统已完成对 Oracle EMR 病程/护理、海量库文书（Vastbase）、检验/检查、病案首页等数据源的接入，质控判定完全依赖 Dify Workflow AI。后续需要：

1. **扩展数据源**：新增 HIS 医嘱、费用明细、手麻系统麻醉记录，与 EMR/检验/检查/护理等形成多源数据底座。
2. **可视化自定义规则质控**：基于上述多源数据，由用户在前端通过组合规则（AND/OR、跨源关联、时序前后）进行质控预过滤，命中规则的病例再进入 Dify AI 二次判定（先规则后 AI）。

新业务库均为**直连 Oracle（同库/同实例）**，可直接复用现有 `oracle_client` 与连接配置，仅需新增视图 SQL 与 source 字段契约。

## 2. 总体架构

```
                                  ┌────────────────────────────┐
   config.json audit_types[i]    │  校验/解密  AuditTypeRegistry │
   ┌──────────────────────┐      └─────────────┬──────────────┘
   │ sources             │                    │
   │  primary (EMR)      │                    ▼
   │  lab / exam         │      ┌──────────────────────────────┐
   │  order (HIS 医嘱)  ◀┼──────┤ data_source_loader           │
   │  fee  (HIS 费用)   ◀┼──────┤  复用 oracle_client           │
   │  anesthesia (手麻) ◀┼──────┤  按 source.backend 选连接      │
   │ group_key/join_rules│      │  canonical 归一 + JoinRule     │
   │ qc_rules[]   ◀ 新增 │      └─────────────┬──────────────┘
   │ ai_filter (开关)    │                    │  PatientBundle[]
   └──────────────────────┘                    ▼
                                  ┌──────────────────────────────┐
                                  │ rule_engine  (新增)           │
                                  │  - 组合条件 AND/OR/NOT         │
                                  │  - 跨源关联 / 时序窗 / 阈值     │
                                  │  - 命中产出 PreFilterHits      │
                                  └─────────────┬──────────────┘
                                  │ ai_filter=off 命中即终态
                                  │ ai_filter=on  命中才送 AI
                                  ▼
                          ┌─────────────────────┐
                          │ payload_composer     │  ← 不改
                          └─────────┬───────────┘
                                    ▼
                          ┌─────────────────────┐
                          │ dify_pusher (可选)   │  ← AI 可关
                          └─────────┬───────────┘
                                    ▼
                          ┌─────────────────────┐
                          │ 结果合并器(新增)      │
                          │ rule_hits + ai_dim   │
                          │ 标注 source=rule/ai  │
                          └─────────┬───────────┘
                                    ▼
                          ┌─────────────────────┐
                          │ _save_audit_results │ ← 复用 schema
                          │ relay_alert/notify  │ ← 不改
                          └─────────────────────┘
```

关键性质：
- 规则引擎位于 loader 之后、payload_composer 之前，**串联在现有 push_executor 内的 payload 阶段之前**，可被 `ai_filter` 开关旁路。
- 关闭规则（`qc_rules=[]`）或不命中时，流程退化为现状；关闭 AI（`ai_filter.enabled=false` 或命中后选择不送 AI）时规则命中即终态出结论，二者解耦。
- **纯规则终态模式**下，需要由规则引擎构造一个兼容 `_save_audit_results` 的 `dify_result` 结构（`dimensions` 来自 RuleHit，`overall_conclusion` 来自规则命中摘要），并生成 `AuditConclusion`，确保 patient_qc / dashboard / relay_alert 等下游链路不依赖 AI 返回。
- 数据源仅是 source 契约的扩展，不改动 `data_source.type` 顶层 schema（顶级仍 oracle/postgresql/emr_vastbase），新源在 source 级显式写 `backend: "oracle"` 即可复用现有连接。

## 3. 数据源扩展设计（HIS 医嘱/费用、手麻麻醉）

### 3.1 设计要点

由于是同实例 Oracle，**无需新增多业务库连接**：
- 新增 3 类 source canonical 契约：`order`、`fee`、`anesthesia`
- 在 `AuditTypeSource.query_sql` 字段编写基于 `jhemr.v_xxx` 或 `his.v_xxx` / `anes.v_xxx` 等视图的 SQL（必要时由 DBA 新增视图或物化视图）
- AuditTypeSource 配置沿用现有结构，仅 `backend/payload` 配合新契约

**前置确认项（P0 启动前必须 DBA/业务确认）**：
1. 医嘱/费用/麻醉视图所在 schema（`jhemr` / `his` / `anes` / `mz` 等），以及 Oracle 用户是否具备 `SELECT` 权限。
2. 费用明细数据量可能极大，SQL 必须带 `{dept_filter}` 与 `:query_date` 过滤，必要时在视图层预聚合或按住院次数过滤，避免全量拉取。
3. 手麻系统的 `operation_no` 与 HIS 医嘱/病案首页的手术号是否存在统一编码，否则跨源关联需要二次映射表。
4. 麻醉记录的"术后"、"术中"、"术前"时间字段是否统一为 `start_time` / `end_time`，时区是否与 EMR 一致。

**数据量与性能约束**：
- `fee` 明细建议只接入"单日计费"或"本次住院汇总"，不要接入历次所有费用。
- `order` 医嘱单患者单次住院可能上千条，规则引擎评估前应在 SQL/视图层做必要聚合（如按药品分类、按长期/临时汇总），或仅在规则命中需要时才全量展开。

### 3.2 新增 source canonical 字段契约

在 `source_field_contract.py` 中新增 3 类。

#### order（HIS 医嘱）
```
canonical: patient_id, visit_number, order_no, order_type(长期/临时),
           order_class(药品/检查/治疗/护理/输血), item_code, item_name,
           dosage, dosage_unit, frequency, route, start_time, stop_time,
           order_doctor, executed_nurse, status(开始/停止/撤销), audit_date
时间键候选: start_time / stop_time / event_time
```

#### fee（HIS 费用明细）
```
canonical: patient_id, visit_number, fee_no, fee_class(药品/耗材/检查/治疗/手术/床位),
           item_code, item_name, spec, price, quantity, total_amount, billing_date,
           charge_dept, audit_date
时间键候选: billing_date / event_time
```

#### anesthesia（手麻系统麻醉记录）
```
canonical: patient_id, visit_number, anesthesia_no, operation_no,
           operation_name, anesthesia_method, anesthesia_doctor, surgery_doctor,
           start_time, end_time, asa_grade, anesthesia_level(一级/二级/三级/四级),
           intraop_events(术中事件摘要), fluids_in, blood_loss, urine_output,
           adverse_events, discharge_anesthesia_status, audit_date
时间键候选: start_time / event_time
```

### 3.3 字段映射与 loader 改造

- `_effective_source_type()` 增加 `order/fee/anesthesia` 分支，仅当 backend=oracle 时调用 `fetch_records`（复用现有 Oracle client）。
- `SOURCE_CANONICAL_FIELDS` 与 `TIME_KEY_CANDIDATES` 在 `source_field_contract.py` 扩展。
- `_apply_join_rules()` 已支持 inner/left join，可直接用于医嘱↔手术、医嘱↔麻醉等跨源关联；需要确认 join_keys 用 canonical 字段（如 `operation_no` 关联 `anesthesia.operation_no`）。
- **新增 source 默认 `load_strategy: "bulk"`**，第一阶段不启用 fanout；后续如需要针对 order 做 fanout，再单独扩展 `_attach_fanout_source`。

## 4. 可视化自定义规则质控设计

### 4.1 规则 DSL（组合条件 + 跨源关联）

存储位置：`audit_type.qc_rules[]`（新增可选字段，缺省 `[]` 即关闭）。

```jsonc
{
  "code": "rule_unique",
  "name": "可读名称",
  "description": "...",
  "severity": "high|medium|low|info",
  "enabled": true,
  "logic": "AND|OR|NOT",
  "filters": [ <filter>, <filter>, {"logic":"OR","filters":[...]} ]
}
```

**filter 字段说明**：
- `from`：source 名称（即 `audit_type.sources` 里的 key，如 `order`、`anesthesia`，不是 canonical type）。
- `field`：该 source 的 canonical 字段名。
- `ref`：引用另一个 source 的字段，格式 `"source_name.field_name"`（如 `"anesthesia.end_time"`）。
- `value` / `values`：标量或数组，用于 `eq/contains/in` 等比较。
- `hours` / `minutes`：时序窗长度。

**filter 原语**（op 取值）：

| op | 语义 | 示例 |
|----|------|------|
| `exists` | 该 source 至少存在 1 条记录；若指定 `field`，则该字段非空 | 医嘱存在抗凝药 |
| `missing` | 该 source 完全无记录，或指定字段全部为空 | 无麻醉记录 |
| `eq/ne` | 字段值等于/不等于标量 | `order.order_type eq "长期"` |
| `contains` | 字符串包含（忽略大小写） | `order.item_name contains "肝素"` |
| `regex` | 正则匹配（默认 Python `re.search`，限制复杂度防 ReDoS） | `progress.content regex "术后.*出血"` |
| `in` | 字段值在数组中 | `fee.fee_class in ["药品", "耗材"]` |
| `gt/lt/ge/le` | 数值比较（自动解析为 float） | `fee.total_amount > 5000` |
| `count_gt/count_ge/count_lt/count_le` | source 记录数比较 | 检验次数 > 20 |
| `any_match` | source 内存在至少 1 条记录满足子 filter 条件 | 病程记录至少 1 条含"贫血" |
| `all_match` | source 内所有记录都满足子 filter 条件 | 所有费用明细 total_amount >= 0 |
| `within_hours_after` | 对 `ref` 字段的某条记录，该 source 在 `[ref, ref+N小时]` 内至少存在 1 条 | 术后 24h 内有病程 |
| `within_hours_before` | 对 `ref` 字段的某条记录，该 source 在 `[ref-N小时, ref]` 内至少存在 1 条 | 术前 1h 有麻醉评估 |
| `none_within_hours_after` | 对 `ref` 字段的**所有**记录，该 source 在 `[ref, ref+N小时]` 内均无记录 | 术后 24h 内无病程 |
| `none_within_hours_before` | 对 `ref` 字段的**所有**记录，该 source 在 `[ref-N小时, ref]` 内均无记录 | 术前 1h 无临时医嘱 |
| `cross_source_eq` | 两 source 的指定字段在 join 后按行相等；未 join 时取各自首条比较 | 首页手术名 == 麻醉手术名 |
| `cross_source_diff` | 两 source 的指定字段不一致 | 医嘱剂量 != 病程记录剂量 |

**时序 op 语义细化**：
- `ref` 字段可能有多条记录（如多次手术）。`within_*` 采用"存在性"语义：只要存在某条 ref 记录使得窗内有数据即命中；`none_within_*` 采用"全称"语义：要求所有 ref 记录对应的窗口内均无数据才命中。
- 时间解析失败时，该 filter 视为 `False` 并记录诊断日志，不阻断整个规则评估。

### 4.2 规则引擎模块

新增 `app/services/qc_rule_engine.py`：

```python
class QCRuleEngine:
    def __init__(self, rules: list[dict]): ...
    def evaluate(self, bundle: PatientBundle) -> list[RuleHit]:
        """返回命中规则列表；每命中产生一个 RuleHit。"""
```

- 纯 Python 实现，无外部依赖，保证测试与离线运行。
- 命中结果 `RuleHit`：
  ```jsonc
  {
    "dimension_code": "anes_no_progress_24h",
    "dimension": "术后24h内无病程记录",
    "severity": "high",
    "issue_summary": "...",
    "recommendation": "...",
    "confidence": 1.0,
    "source": "rule",                  // 区分维度来源（ADR 扩展）
    "extra": { "evidence_anesthesia": {...}, "evidence_progress": {...} }
  }
  ```
- 与 ADR-2 维度数组结构完全兼容，可无缝落库到 `AuditDimensionResult`，`extra_json` 存证据。

### 4.3 与 Dify AI 的协同（预过滤）

在 `push_executor` 现有 pipeline 中插入节点（**仅当 audit_type 配置了非空且至少一条启用的 `qc_rules` 时启用**，否则维持原逻辑）：

```
PatientBundle
   │
   ├─ qc_rules 未配置/全禁用 ──否──> 直接到 payload_composer / dify_pusher（现状）
   │
   ▼ 是
QCRuleEngine.evaluate(bundle)  →  RuleHit[] / []
   │
   ├─ ai_filter.enabled=false 或命中后选择终态
   │      命中 RuleHit[] → 构造 dify_result(dimensions=RuleHits, overall_conclusion=规则摘要)
   │                    → 生成 AuditConclusion → 落库 / relay / 通知（终态，不调用 Dify）
   │      未命中      → status=ok，可 optionally 标记 skip_reason="rule_pre_filter_pass"
   │
   └─ ai_filter.enabled=true
           命中 RuleHit[] → 将命中摘要写入 `payload["rule_context"]` → payload_composer
                            generic_multi_source builder 识别 rule_context 并前置到 mr_text
                            → 送 Dify AI → AI 维度标注 source=ai；RuleHit 标注 source=rule；统一合并落库
           未命中        → 按 ai_filter.send_on_no_hit：
                             true  走原 payload_composer / dify_pusher 流程（兼容旧行为）
                             false 标记 skip_reason="rule_pre_filter_pass"，不送 AI
```

**关键实现细节**：

1. **payload builder 适配**：`generic_multi_source`  builder 在渲染前检查 `payload.get("rule_context")`，若存在则在 `mr_text` 最前面追加一段"【规则预筛命中】"摘要（含 dimension_code / severity / 问题摘要），再拼接各 source 原始内容。这样 Dify 输入仍为字符串，且 AI 能聚焦可疑点。

2. **纯规则终态的结论生成**：`app/services/rule_conclusion_builder.py`（新增）负责把 `RuleHit[]` 转换为：
   - `dify_result.dimensions`：与 ADR-2 完全兼容，每条 `source="rule"`。
   - `dify_result.overall_conclusion`：自然语言摘要，如"命中 2 条规则：术后无病程记录、麻醉记录缺失"。
   - `AuditConclusion`：写入 `overall_conclusion`、`focus_items`（命中规则列表 JSON）、`overall_qc_summary`。
   - `PushLog.inconsistency`：命中任何 high/medium 规则时设为 `true`；仅 info 时为 `false`。

3. **severity → alert_level 映射**：规则 severity 与现有 AI severity 统一映射：
   - `high` → `red`
   - `medium` → `yellow`
   - `low` → `blue`
   - `info` → `gray`
   该映射同时用于 `PushLog.alert_level` 和 `AuditDimensionResult.alert_level`，保证 relay_alert / 通知 / dashboard 颜色口径一致。

4. **维度合并器 `dimension_merger.py`**：
   - 按 `dimension_code` 去重；AI 与 rule 同时命中同维度时 `source="both"`。
   - severity 冲突取高（high > medium > low > info）。
   - `extra` 证据对象做浅合并（key 冲突时 rule/ai 证据分别放入 `extra.evidence_rule` / `extra.evidence_ai`）。

5. **`PushLog.skip_reason` 新增值**：
   - `rule_pre_filter_pass`：规则未命中且 `send_on_no_hit=false`，本次不送 AI。
   - `rule_engine_error`：规则引擎异常（捕获后跳过，避免污染批次）。

6. **relay_alert / notify**：仍按 `relay_alert.severity_levels` 筛选 high/medium 等维度，无需改动；规则命中高危项自然进入告警队列。

```
        ├ 规则列表（表格：code/name/severity/enabled）
        ├ 拖入数据源字段卡片 → 自动生成 filter（与单选条件块）
        ├ 条件块可嵌套：AND/OR/NOT 容器（缩进树形）
        ├ 跨源关联条件：选择 from/ref source.field（下拉自动列出 canonical 字段）
        ├ 时序条件：可视化时间轴（轴向拖拽 N 小时窗）
        ├ AI 协同开关：ai_filter.enabled / send_on_hit / send_on_no_hit
        └ 实时预览：右侧"试运行"按钮，按当前规则对一个真实 PatientBundle 模拟命中
```

组件复用 Element Plus：条件块用 `el-tree` + 折叠面板，字段下拉用 `el-select`，时序用滑块。试运行调用新增 `/api/audit-types/{code}/rule-dry-run` 端点，返回命中预览，不落库不推送。

### 4.5 source 字段与 display 渲染一致性

为避免规则维度与 AI 维度在前端展示不统一，采用以下约定：

- **统一走 `dimensions` 路径**：无论规则还是 AI，命中结果都注入 `dify_result.dimensions`，`render_engine.js` 的 `dimension_grid` / `table` / `severity_badge` 等块无需感知来源差异。
- **source 徽章**：在 `AuditDimensionResult` 增加独立列 `source`（默认 `ai`），前端维度列表按 `source` 渲染小徽章：
  - `rule`：蓝色（规则命中）
  - `ai`：橙色（AI 产出）
  - `both`：紫色（规则预筛 + AI 确认）
- **display 配置示例修正**：不再使用 `path: "$.rule_hits"`，而是复用现有 `$.dimensions`：
  ```jsonc
  { "label": "质控维度", "path": "$.dimensions", "type": "dimension_grid" },
  { "label": "总体结论", "path": "$.overall_conclusion", "type": "text_block" }
  ```
- **extra 证据展示**：`dimension_grid` 对 `extra` 对象提供折叠查看，规则证据（`evidence_order`、`evidence_anesthesia` 等）与 AI 证据在同一位置展示。

## 6. ORM / 迁移

**几乎零迁移**：
- `qc_rules` / `ai_filter` 存在 `audit_types[]` JSON（config.json），不进库。
- `AuditDimensionResult` 增加 `source` 字段（默认 `ai`，迁移回填历史值为 `ai`），存放规则/AI 来源；其它字段不变。
- `AuditConclusion` 表结构不变，纯规则模式下由 `rule_conclusion_builder.py` 生成记录。
- `PushLog.skip_reason` 为字符串列，新增值不需 DDL，仅前端文案与导出兼容。
- `QCRecordAlertLog` / `relay_alert_service` 不变，自动覆盖规则命中高危。

迁移步骤（手动迁移 `database.py`）：
1. `_verify_required_schema`：增加 SQLite 与 Oracle 兼容的 `audit_dimension_result.source` 列（VARCHAR(16)），默认 `'ai'`。Oracle 模式下该列置于 CLOB 列之前，避免 ORA-24816。
2. 历史 NULL 行回填：`UPDATE ... SET source='ai' WHERE source IS NULL`。
3. CSV / `/api/logs` 导出过滤已隐含容忍 NULL，仅追加新值即可。
4. 规则命中且关闭 AI 时，`PushLog.ai_result` 写规则摘要 JSON，保持该字段非空便于排查。

## 7. 回归风险与保护项

| 风险点 | 保护措施 |
|--------|----------|
| Dify 单一输入必须为字符串 | 规则摘要写入 `payload["rule_context"]`，由 builder 前置到 `mr_text`；关闭 ai_filter 时跳过 AI |
| bulk 事务隔离（一例失败不污染批次） | 规则评估在 push_executor 单例事务内，异常捕获写 `skip_reason="rule_engine_error"` 并继续 |
| 内置 6 类 audit_type 行为回归 | 内置类型不写 `qc_rules`，等价现状；仅当用户显式为某类型添加规则才生效 |
| 旧维度 medical_evidence_json / nursing_evidence_json | 规则维度走 `extra_json`，不污染旧字段（ADR-2 已锁） |
| relay_alert / 关键 push 流程 | 维度合并后仍由 `enqueue_high_severity_alerts` 统一处理，逻辑不变 |
| 调度器双模式 / 运行锁 | 规则评估在最内层，不接触调度，不影响 dual mode |
| Oracle 大写列名 | 复用现有 oracle_client 与 `.lower()` 规一，新源 SQL 仍经 `validate_configurable_sql` |
| 新 source schema/权限不确定 | P0 启动前 DBA 确认 schema、视图、权限；SQL 模板先走 test-source 端点验证 |
| 费用/医嘱数据量大导致推送超时 | 新源 SQL 强制 `{dept_filter}` + `:query_date`；规则引擎增加单例评估超时（默认 5s）；大数据量源先做视图聚合 |
| regex 规则 ReDoS | 正则匹配增加超时（默认 1s）与长度限制（默认 1KB），超时报错并标记 `rule_engine_error` |
| 敏感数据（费用明细）泄露 | 费用 source 默认不加入 `mr_text` 全量明文；display 中对费用类证据做脱敏或折叠；权限上可单独配置"费用数据查看"角色 |
| 前端 audit_types.html 既有功能 | 规则编辑 tab 默认折叠，无 `qc_rules` 时显示"未启用"占位 |

# AI 协作规则（多 AI 统一约束）

> 适用范围：在本仓库工作的所有 AI（ZCode/Codex/Claude/外部复核 AI 等）与人类开发者。
> 生效日期：2026-08-24。本规则与 `AGENTS.md` 冲突时，以 `AGENTS.md` 为准并立即报告冲突。
> 核心痛点：多个 AI 轮换接手，历史上出现过散文件乱放、改动不留痕、交接靠聊天记忆的问题。本规则就是堵这些洞。

---

## 1. 会话启动协议

1. 按 `开发起步包/README.md` §1 的顺序读文件。
2. 读 `01_统一修改记录.md` **最后 10 行**，确认：生产处于什么状态、上一任留下了什么未完成事项。
3. 若上一任的变更未登记，先向用户报告，不要默认其有效。

## 2. 统一修改记录制度（强制，违者变更不被承认）

**任何会话**只要满足以下任一条件，结束前**必须**在 `01_统一修改记录.md` 表格末尾追加一行：

- 修改了仓库内任何文件（代码/文档/配置/脚本）；
- 对生产环境（10.10.8.84 容器、Oracle 应用库、配置、镜像）执行了任何操作；
- 删除/移动/归档了任何文件。

字段要求：

| 字段 | 要求 |
|---|---|
| 日期 | YYYY-MM-DD（跨天写起止） |
| 执行者 | AI 名称/模型（如 `ZCode/GLM-5.3`、`Codex`）或人名；不确定就写 `未署名AI` 并注明推测依据 |
| 类型 | 代码 / 文档 / 数据整改 / 生产部署 / 目录整理 / 复核 / 交接 之一 |
| 摘要 | 一两句话说清做了什么；涉及数字必须给数（降级条数、患者数等） |
| 影响范围 | 关键文件路径或表名；多的写"详见 XXX 文档" |
| 生产写入 | 无 / 有（有则必须写明授权来源、备份位置、回滚点） |
| 证据 | 交接文档编号、备份 JSON 路径、commit hash、日志位置 |

补充规则：

- 一行不够可以加缩进行，但**不得改写历史行**（append-only）；发现历史行错误时新增更正行。
- git 提交后把 commit hash 补记到该行（提交本身也需用户批准，见 §6）。

## 3. 文件放置规则（散文件治理）

| 资产类型 | 唯一允许的位置 | 命名规范 |
|---|---|---|
| 运维/整改/生成脚本 | `scripts/` | `*_YYYYMMDD.py`（日期后缀强制） |
| 计划/交接/复核文档 | `docs/ACTIVE/` | `NNN_描述_YYYYMMDD.md`（编号向 `docs/INDEX.md` 取下一个） |
| 整改证据/备份 JSON | `docs/remediation/` | `*_YYYYMMDD.json` |
| 截图、导出附件（含 PHI） | `docs/attachments/` | `描述-YYYYMMDD/` 目录包裹；**禁止提交 git、禁止外发** |
| 历史参考契约 | `docs/reference/` | 沿用 101+ 编号 |
| 过时/清理出的资产 | `docs/archive/` | `清理主题-YYYYMMDD/` 目录包裹 |
| 配置历史备份 | `config/backups/` | 沿用 save_config 时间戳格式 |
| 根目录 | **只允许**仓库级说明（AGENTS/CLAUDE/ARCHITECTURE/DEPLOY/README_CN）与部署必需文件（Dockerfile/compose/requirements 等） | 新增需先在 `开发起步包/README.md` §3 地图登记 |

任何 `docs/**/*.md` 的新增/移动/归档，**同一变更内**必须同步 `docs/INDEX.md`（AGENTS.md 既有规则）。

## 4. 生产写入红线

- 生产（容器/Oracle 应用库/配置/镜像/Dify/Relay）默认**只读**；写入必须：
  1. 有用户当次明确授权（"可以降级"这类话要能对应到具体范围和数量）；
  2. 写前备份（数据整改必须先产出 dry-run 明细 JSON 落 `docs/remediation/`）；
  3. 提供回滚点（备份文件/配置快照/镜像 tag）；
  4. 写后 verify 并把结果记入 `01_统一修改记录.md`；
  5. 热更新容器文件后必须 `docker commit` 持久化并在记录中留镜像信息。
- 批准单口径服从 `docs/ACTIVE/023` §9.1；024/025 文档中的"不授权"清单继续有效。

## 5. 交接规范

交接文档（docs/ACTIVE/NNN_*HANDOVER*）必须包含：访问方式、关键数字、逐条验证结果、残留风险、回滚方案、给下一任的核查清单。参考 024/025 的结构。

## 6. git 提交规范

- **用户未明确要求时不提交**；多 AI 的未提交改动混在工作区时，提交前必须逐文件核对归属（对照 `01_统一修改记录.md`），不得把别人的半成品一起提交。
- 提交信息沿用现有格式：`类型(范围): 中文摘要`，例如 `fix(parser): 契约校验器只降不升`。
- 提交后补记 hash。

## 7. 隐私红线

- 患者标识、病历原文、含 PHI 的 Excel/截图：不出仓库目录、不进 git、不贴进任何文档正文、不发给公网模型。
- 外发复核只允许脱敏包（参考 `.agents/skills/med-audit-history-remediation` 的脱敏规则）。

## 8. 违规处理

- 未登记变更：下任 AI 拒绝基于其继续，报告用户裁定保留或回滚。
- 散落新文件：发现即移入 `docs/archive/stray-发现日期/` 并登记，不改内容。
- 本规则的修订：需用户批准，并在 `01_统一修改记录.md` 登记。
